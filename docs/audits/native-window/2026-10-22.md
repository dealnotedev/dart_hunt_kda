# Native window layer audit — October 22, 2026

The audit examined the new implementation in the working tree: `windows/runner`,
the local `bitsdojo_window` code, Dart FFI and geometry in `lib/window`, the tray
integration, and application startup. The user's problematic build is an **older
build**. Findings about the new implementation do not establish the cause of the
older build's failure; shared code paths are identified below. Application
behavior was not changed as part of this audit.

Main finding: replacing a monitor can affect DPI, window placement, and graphics
initialization. The code has specific weaknesses in these scenarios. However,
"no window and no tray icon" is more consistent with incomplete startup or tray
initialization failure than with window placement alone. The failure on the
user's computer was not reproduced, and no dump or startup log is available.

## Significant findings

### A01 — P1: a missing first frame leaves the application without a window or tray icon

Locations: `lib/window/window.dart:16`, `lib/main.dart:27`,
`windows/runner/bitsdojo_window/bitsdojo_window.cpp:535`,
`windows/runner/flutter_window.cpp:45`.

`doWhenWindowReady` waits indefinitely for `waitUntilFirstFrameRasterized`.
Only then does it allow the window to be shown and create the tray icon. Before
that permission is granted, the native handler removes `SWP_SHOWWINDOW`,
including attempts to show the window from the first native frame callback.
Incomplete rasterization leaves a running process without either user entry
point. There is no independent startup health check or error notification.

The native `hidden_start` probe confirms that showing the window is blocked
until readiness. It models a missing readiness signal; an actual GPU hang was
not reproduced. Hidden startup is also a general risk in the older build, but
the new waiting mechanism must be evaluated separately.

Recommendation: create a native log before Flutter starts, define
`creating / waiting_for_frame / ready / failed` startup states, and add a native
watchdog. On timeout, display a system message or diagnostic window. A Dart
timeout helps, but cannot recover from a blocked Dart isolate or UI thread.
Tray initialization and diagnostics should not depend entirely on the first
Flutter frame.

### A02 — P1: tray failure in silent mode leaves a hidden process

Locations: `lib/main.dart:34`, `lib/tray.dart:59`.

With `-silent`, the window is hidden before `createTrayIcon` runs. If icon
creation, image loading, or `setVisible(true)` fails, the integration calls
`dispose()` and throws an exception. The caller neither handles the error nor
restores the window. `doWhenWindowReady` also returns a Future that `main`
neither awaits nor handles.

A temporary `Shell_NotifyIconW(NIM_ADD)` failure while the taskbar is unavailable
is particularly relevant. The installed cnativeapi 0.5.2 dependency supports
recovery after `TaskbarCreated`, but disposing the icon removes its subscription.
The dependency's source was inspected; the user's Explorer was not restarted,
and a Shell failure during startup was not reproduced dynamically.

Recommendation: allow silent mode only after the tray icon has been created
successfully. Add bounded retries and fall back to a visible window after a
permanent failure. Distinguish a temporary registration failure from an
unrecoverable object creation error. This is a specific weakness of the new
tray integration; the older code needs separate evaluation.

### A03 — P2: Show does not recover a window from a disconnected display

Locations: `lib/window/window.dart:198`, `lib/tray.dart:18`,
`windows/runner/win32_window.cpp:129`.

`show()` uses `SWP_NOMOVE | SWP_NOSIZE`, preserving the current coordinates.
Neither showing the window from the tray nor the second-launch path checks
whether the window intersects an available monitor. There is no custom response
to changes in display topology or work areas. If the window ends up outside all
displays and Windows does not relocate it, Show does not correct its position.

The `offscreen_show` probe deliberately places a window outside the virtual
desktop and then uses the same native show path. Result:
`visible=1 intersects_monitor=0`. This tests recovery from an off-screen
position, rather than physically disconnecting a monitor.

Recommendation: use a shared `restoreAndEnsureVisible` operation for the tray
and second-launch handling. Check actual monitor intersection, select the
nearest `rcWork`, move an inaccessible window inside it, and then show and
activate the window. Do not recenter a window that is already accessible.
[MonitorFromWindow](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-monitorfromwindow)
can distinguish actual intersection from selecting the nearest display.

On a **completely new startup**, this code does not read geometry from a
previous run: it creates and centers a new window. Therefore, "coordinates
from the old monitor were saved" is a weak explanation for a cold-start
failure. The risk is greater for an existing background process, a hidden
window, and recovery after display configuration changes.

### A04 — P2: repeated launches lack a reliable handoff protocol

Location: `windows/runner/win32_window.cpp:126`.

Checking the mutex and finding the window are separate operations. The first
process may have created the mutex without creating its HWND yet. A second
process then sees the mutex, receives a null HWND, and exits after unsuccessful
Win32 calls. Searching only for the `hunt_stats` title is fragile if the title
changes and does not check the window class or owner. Results from `CreateMutex`,
`GetWindowPlacement`, `GetClientRect`, `ShowWindow`, and `SetWindowPos` are not
checked. Mutex access failures are not handled separately.

The second process also calls `ReleaseMutex` even though opening an existing
mutex does not grant ownership. Under the
[ReleaseMutex contract](https://learn.microsoft.com/en-us/windows/win32/api/synchapi/nf-synchapi-releasemutex),
that call fails. This is not a "mutex stuck after a crash": the kernel releases
process resources. The main risk is a hidden process that is still running.

Recommendation: use a dedicated single-instance object with an RAII handle;
capture the creation result and error code; use a stable IPC identity; wait for
HWND readiness with a bound; and request activation from the first process with
an acknowledgment. The window owner should restore geometry on its own UI
thread. This code is inherited from the older implementation. The interprocess
scenario was not run dynamically during the audit to avoid using the running
application's mutex.

Correction to an earlier chat hypothesis: calling `FindWindowA` between
`CreateMutex` and `GetLastError` cannot be treated as a proven source of error
code corruption.
[FindWindowA is documented not to modify last error](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-findwindowa).
Capturing the error code immediately is still sensible, but this call order
alone does not establish a bug.

### A05 — P2: WM_SYSCOMMAND is decoded incorrectly

Location: `windows/runner/bitsdojo_window/bitsdojo_window.cpp:505`.

Comparisons such as `wparam == SC_MINIMIZE / SC_MAXIMIZE / SC_RESTORE` ignore
system-reserved low bits. The command must be decoded with
`const auto command = wparam & 0xFFF0`, as required by the
[WM_SYSCOMMAND contract](https://learn.microsoft.com/en-us/windows/win32/menurc/wm-syscommand).

The `commands` probe uses the actual subclass: plain SC_MINIMIZE sets
`during_minimize` to 1 in the underlying window handler, whereas valid
SC_MINIMIZE with low bits set to 2 leaves it at 0. Consequently, WM_SIZE
suppression depends on how the same command is sent. The pattern also exists
in the older 0.1.6 package. This is a window-command handling defect, not proof
of the cause of a cold-start failure.

### A06 — P2: consecutive Dart setters can lose the requested size

Locations: `lib/window/window.dart:81`, `lib/window/window.dart:122`,
`lib/window/window.dart:143`, `lib/window/window_util.dart:29`.

Geometry changes are posted with PostMessage, while reading rect synchronously
returns geometry already applied to the HWND. In the sequence
`window.size = newSize; window.alignment = Alignment.center;` outside the
readiness callback, the second setter can read the old size before the first
command is handled and post that old size back. `_sizeSetFromDart` is used only
inside `_isInsideWindowReady`, so this provides only partial protection.

Recommendation: use one atomic geometry command containing logical size and
alignment, calculated on the UI thread, or a command queue with acknowledgments
and a shared pending state. The current `main` configures initial geometry
inside the protected callback; this finding concerns subsequent API use. The
conclusion comes from code inspection; the complete Dart/Flutter scenario was
not reproduced dynamically.

### A07 — P2: WM_FONTCHANGE dereferences an unready controller

Location: `windows/runner/flutter_window.cpp:80`.

MessageHandler checks the controller at its start, but the WM_FONTCHANGE branch
does not. Receiving this message before readiness or during partial teardown
makes `flutter_controller_->engine()->ReloadSystemFonts()` unsafe. Add
controller/engine checks and align message handling with their lifecycle.
This is also inherited from the Flutter runner template; being present in the
template does not make the dereference safe. The rare scenario was not
reproduced dynamically.

## DPI, performance, and outdated implementation choices

1. **Unnecessary resizing before applying the new DPI rectangle.**
   `bitsdojo_window.cpp:486` calls `forceChildRefresh()` before forwarding
   WM_DPICHANGED to the main handler. It calls SetWindowPos twice, first with
   `width+1,height+1` and then with the original size. The `dpi_order` probe
   recorded two child HWND WM_SIZE messages before the parent applied the
   suggested RECT. This reproduces unnecessary work that may complicate
   graphics-surface recreation. A resulting GPU hang has not been established.
   Keep one sizing path: new DPI -> suggested RECT -> final client area -> child
   size. [WM_DPICHANGED](https://learn.microsoft.com/en-us/windows/win32/hidpi/wm-dpichanged)
   defines the suggested RECT's meaning. The 1px pattern also exists in the older
   package.

2. **Do not blindly remove manual WM_DPICHANGED_BEFOREPARENT dispatch.**
   `bitsdojo_window.cpp:328` sends this synthetic message when the child is
   created. It is a workaround related to Flutter DPI initialization. The
   inspected [source for the engine revision in use](https://github.com/flutter/flutter/blob/deb287481e3ce9468f3434937ced4240a70539ca/engine/src/flutter/shell/platform/windows/flutter_window.cc)
   starts with the primary monitor's DPI and updates it through this message.
   A replacement must be tested on startup on a secondary display with a
   different DPI, rather than only on the primary monitor.

3. **Changing WINDOWPOS after the window has moved does not correct the window.**
   `bitsdojo_window.cpp:542` modifies the structure again in WM_WINDOWPOSCHANGED.
   That write does not move an already positioned window. Corrections belong in
   WM_WINDOWPOSCHANGING or a separate deliberate operation. Several branches,
   including `bypass_wm_size`, are effectively never enabled in the current code.

4. **maxSize limits tracking without setting the maximized size.**
   `bitsdojo_window.cpp:565` changes ptMaxTrackSize but not ptMaxSize. At DPI 144,
   the `max_limit` probe produced `1200x900` while `3000x1800` remained unchanged,
   respectively. This checks message fields; actual maximization of a real
   Flutter window was not tested. Define the maxSize contract and test maximize,
   Snap, and movement between displays.
   [MINMAXINFO](https://learn.microsoft.com/en-us/windows/win32/api/winuser/ns-winuser-minmaxinfo)
   distinguishes these fields. A limit on just one axis is also ignored entirely
   by the current requirement that both components be nonzero.

5. **WH_CBT and internal class-name discovery are unnecessary in an owned runner.**
   Win32Window already knows the parent HWND, and FlutterView exposes the child
   HWND. Prefer explicitly attaching the window layer to these handles, using
   one owner for UI commands, and checking subclass results without class-name
   discovery. This reduces dependence on creation order and Flutter internals.
   Atomic HWND values do not by themselves solve window lifetime or handle reuse.

6. **PerMonitorV2 is already configured correctly.**
   It should not be disabled because of a new monitor. Calling
   EnableNonClientDpiScaling for PMv2 is redundant:
   [Windows already performs this work](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-enablenonclientdpiscaling).
   Older Windows 7/8/8.1 compatibility-manifest GUIDs do not establish support for
   those systems and should match the project's support policy. The presence
   of GetDpiForWindow in a DLL establishes API availability, not the actual
   window's DPI awareness; `isDPIAware` is currently a misleading name.

7. **Native failures are mostly unobservable.**
   Add a local log in a user-writable directory recording startup phase, HWND
   and parent/child rectangles, DPI/awareness, selected monitor/rcWork, graphics
   initialization HRESULTs, Win32 errors, tray creation, and the first frame.
   Returning EXIT_FAILURE alone explains nothing to the user. Dart exceptions
   should also be logged.

8. **Small but real runner defects.**
   `while (GetMessage(...))` does not distinguish a -1 result and needs an error
   path. The CoInitializeEx HRESULT is unchecked, and COM is uninitialized before
   the stack-allocated FlutterWindow is destroyed; use RAII and correct ordering.
   `Win32Window::Show()` returns prior visibility from ShowWindow even though its
   comment promises success. Utf8FromUtf16 includes the terminating NUL in
   std::string; the newer SDK template uses an explicit length. The console
   helper reverses the freopen_s check and duplicates stderr from stdout. These
   points do not establish the cause of the failure after replacing a monitor.

Impeller is already disabled in the current `main.cpp:25`. That line was added
outside this audit. It does not eliminate graphics usage by another renderer or
remove the first-frame dependency of the window and tray. An observable backend
selection and comparison on the affected computer would be more useful.

## Completed checks and confidence limits

The standard `windows/tests` target was built with MSVC 19.44 / Windows SDK
10.0.26100. CTest: **1/1 passed**. It creates test window classes using
DefWindowProc, does not start the Flutter engine, and does not include the
production runner's PMv2 manifest. It does not establish correctness of actual
DPI transitions or graphics surfaces.

The additional `probe.cpp` harness compiles the **actual local window C++ code**,
enables PMv2, and reported DPI 144 on this machine. Its underlying host/child
handlers are test implementations; it does not run the complete Flutter engine.

The current Flutter smoke test also has a weak close-to-tray check: it hides
the window first, then closes it, and checks only that it remains invisible.
It should check that a valid HWND survives, Show works after Close, and engine
interaction remains live. Otherwise, it can miss window destruction.

## Fix priorities and follow-up validation

1. Reliable bootstrap: logging before Flutter, independent hang diagnostics,
   readiness and tray error handling, and a visible fallback for silent mode.
2. A shared window recovery command and single-instance handoff, plus the
   WM_SYSCOMMAND mask. These are small changes with clear validation paths.
3. A simpler DPI path with removal of confirmed redundant resizing after
   validation in real Flutter; atomic geometry and a consistent UI thread.
4. Removal of unnecessary hook/compatibility workarounds, correct shutdown,
   and RAII.

Test the real runner at 100/125/150/200% scaling on two monitors with different
DPI, including a secondary display to the left or above with negative
coordinates; startup with the pointer on the secondary display; display
disconnection while visible and hidden; sleep/resume; resolution changes;
silent startup with an unavailable tray; first-frame delay/failure; two
simultaneous launches; and relaunch with an unresponsive first instance.
Use a test environment for monitor and Explorer operations.
